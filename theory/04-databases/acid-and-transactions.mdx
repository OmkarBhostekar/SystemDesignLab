# ACID and Transactions

> A transaction is a deliberate boundary around a set of state changes whose invariants must survive concurrency and failure.

## Why This Exists

Suppose a wallet transfer debits Alice and credits Bob. The naive design sends two independent updates. A process crash between them creates money from nowhere or destroys it. Concurrent transfers can also observe an intermediate balance, and a successful response can be lost if the client times out before learning whether the commit happened.

A transaction groups the changes so other transactions observe an all-or-nothing outcome. It does not make every operation globally safe, does not cross service boundaries automatically, and does not replace idempotency or backups. Its value comes from choosing the narrowest boundary that protects a stated invariant.

## Mental Model

| Property | Practical question | What it does not promise |
| --- | --- | --- |
| Atomicity | Are all changes applied, or none? | A retry is duplicate-safe, or an external side effect is undone |
| Consistency | Does a committed state satisfy declared invariants/constraints? | The database knows every business rule unless encoded or checked |
| Isolation | What can concurrent transactions observe or change? | No contention, deadlocks, or serialization retries |
| Durability | After acknowledgment, can a crash lose the commit? | Backups, region survival, or protection from operator error |

“Consistency” in ACID means transition from one valid database state to another under constraints; it is not the same phrase as a distributed system's read consistency model. Always name the exact guarantee and scope.

## How It Works

A typical transaction lifecycle is:

```text
begin → read/check → write → prepare commit → durable log flush → commit visible
  └────────────── failure ────────────────→ rollback / recovery
```

The database tracks the transaction's changes and concurrency metadata. With write-ahead logging (WAL), log records describing changes are flushed before data pages, so crash recovery can redo committed changes and discard incomplete ones. The exact visibility and lock behavior depends on the isolation level; see [transaction isolation](transaction-isolation.mdx).

Keep transactions short and deterministic. Put validation and the writes that protect the invariant inside the boundary, but not network calls, user input, sleeps, or a payment provider call. If an external call must participate, record an intent in the local transaction and use an idempotent workflow/reconciliation step rather than pretending a database commit can atomically control the provider.

## Example

For a wallet transfer, define the invariant: **the sum of all wallet balances plus held funds is conserved, and a transfer is applied at most once for its idempotency key.** A relational implementation can:

```sql
BEGIN;

-- Lock or otherwise serialize the two wallet rows in a stable order.
UPDATE wallets SET balance = balance - 100
WHERE wallet_id = 'alice' AND balance >= 100;

-- Verify one row changed, then insert a unique transfer idempotency key.
INSERT INTO transfers (idempotency_key, source_id, destination_id, amount)
VALUES ('client-7f', 'alice', 'bob', 100);

UPDATE wallets SET balance = balance + 100 WHERE wallet_id = 'bob';
COMMIT;
```

The naive two-request version fails on a crash and on duplicate client retries. The improved transaction protects local rows and a unique key. The new trade-off is contention: hot wallets serialize, deadlocks are possible if lock order differs, and a client may need to retry a serialization/deadlock failure. If a payment processor is also involved, the transaction cannot roll back money already captured; model states such as `authorized`, `captured`, `refund_pending`, and a reconciliation job instead.

Atomicity also has a scope. A database transaction can cover several tables in one database, but not arbitrary queues, caches, email sends, or another service unless a distributed transaction protocol is deliberately used. Even a distributed transaction adds coordinator, timeout, recovery, and availability costs; it is not “ACID across the internet for free.”

## Scaling Behavior

Transaction cost grows with rows touched, indexes maintained, log volume, lock/snapshot lifetime, and contention—not just statement count. Larger transactions hold resources longer and make retries more expensive. At higher write rates, a hot account or counter can become a serialization point even with many database nodes.

Partitioning can improve scale only when the transaction boundary remains local. If a transfer crosses shards, choose an explicit distributed protocol, a workflow with compensating actions, or a data ownership change. Measure commit latency, lock waits, active transactions, WAL/redo throughput, aborts, and replica apply lag.

## Failure Modes

- **Crash before commit:** Changes must be rolled back or absent after recovery.
- **Client timeout after commit:** A retry can duplicate the effect unless an idempotency key/unique constraint returns the original outcome.
- **Deadlock:** Two transactions acquire locks in different orders; the database aborts one and the application retries the whole transaction safely.
- **Long transaction:** User think time or a network call holds locks/snapshots, causing queueing and bloat.
- **External side effect split:** Database commit succeeds but email/payment/queue publish fails; use an intent/outbox-style workflow and reconciliation.
- **Replica/read confusion:** A write commits on the primary but a lagging read replica does not show it immediately.
- **False durability:** A commit reaches one durable device but backups or another region are not current.

## Trade-offs

Transactions simplify invariants and recovery reasoning but consume locks, memory, log bandwidth, and concurrency. Stronger isolation can prevent anomalies at the cost of blocking or abort/retry work. Distributed transactions can preserve atomic semantics across participants but add coordination and failure states. Workflows and compensations improve decoupling and availability but expose intermediate states and require idempotency/reconciliation.

## Alternatives

- **Single-statement conditional update:** Best for a one-row invariant such as decrement-if-positive.
- **Local transaction plus outbox/intent:** Best when durable local state must trigger asynchronous external work.
- **Saga/workflow:** Best for multi-service steps with explicit compensation rather than one atomic commit.
- **Event-sourced append:** Best when an immutable history and deterministic projections matter; it still needs concurrency/version rules.
- **Distributed transaction/2PC:** Consider only when participants and availability/latency costs are acceptable and recovery is operable.

## When to Use

Use a transaction when multiple changes must obey one invariant and share a manageable authority. Define the boundary, isolation, retry condition, timeout, and idempotency behavior before writing the SQL or API call.

## When Not to Use

Do not wrap unrelated reads, network calls, or long workflows in one transaction. Do not use a transaction to hide an ownership boundary or to claim exactly-once behavior for an external effect. A successful database commit is not evidence that a client saw the response or that every derived system has updated.

## Common Misconceptions

- **ACID means globally consistent across services.** It usually describes one engine and an explicit transaction scope.
- **Durability means backups and disaster recovery.** WAL/commit durability and restore/region objectives are separate.
- **Atomicity means retries are safe.** A retry after an unknown outcome needs idempotency.
- **Serializable means no failures.** It may abort transactions and requires a bounded, correct retry loop.
- **One huge transaction is safer.** It may increase contention, lock duration, log usage, and blast radius.

## Interview Lens

### 30-Second Explanation

> I use a transaction to protect a named invariant across a bounded set of changes. Atomicity gives all-or-nothing visibility, constraints define valid committed states, isolation controls concurrent observations, and durability covers crash recovery after commit. I keep the transaction local and short, make retries idempotent, and use an intent/workflow with reconciliation for external services rather than claiming a database transaction is distributed exactly-once.

### When to Introduce It

Introduce transactions when a requirement says “never oversell,” “debit and credit together,” “unique once,” or “all fields change together.” Name what can remain eventually consistent.

### Common Follow-Ups

- Which rows/tables are in the transaction?
- What isolation level and lock order are needed?
- What happens when the client retries after a timeout?
- What if the external payment or queue call fails?
- What does a committed write mean for replicas/backups?

### Common Candidate Mistakes

- Calling two service requests a transaction without a protocol.
- Holding a transaction open across a remote call.
- Forgetting deadlock/serialization retries and idempotency.
- Treating a cache, search index, or email as atomically committed.
- Confusing ACID consistency with distributed read consistency.

## Summary

- ACID properties answer different failure/concurrency questions and have a defined scope.
- Choose the smallest transaction that protects a local invariant; keep it short and retryable.
- WAL and commit acknowledgment support crash recovery, not backups or global durability.
- External side effects need intents, idempotency, and reconciliation or an explicitly chosen distributed protocol.
