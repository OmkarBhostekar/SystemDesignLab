# Database Replication

> Replication creates additional copies of state; it does not automatically make reads fresh, writes available, or failover safe.

## Why This Exists

A single database instance can become a read bottleneck or a single failure domain. The naive improvement is to copy it and send reads everywhere. That serves stale data during lag, can route a correctness decision to a replica that has not applied a write, and may promote two leaders during a network partition.

Replication is a protocol about ownership, log/order transfer, acknowledgment, and promotion. First decide why copies exist: read scale, local latency, crash durability, or regional recovery. Then define which copy is authoritative for a write and what a successful acknowledgment means.

## Mental Model

| Choice | What it buys | Price/limit |
| --- | --- | --- |
| Leader/follower | One write order and simple authority; followers can serve reads/backups | Write bottleneck, lag, promotion/fencing complexity |
| Synchronous follower | Commit waits for selected copy/copies | Higher write latency and reduced availability if required followers fail |
| Asynchronous follower | Low write latency and more write availability | A crash can lose unshipped acknowledged writes; stale reads |
| Multi-leader | Writes local to regions/owners | Conflicts, ordering, and reconciliation |
| Leaderless/quorum | Multiple replicas can accept/read with tunable thresholds | Read repair/version conflicts, quorum availability/latency trade-offs |

“Replica” can mean a physical copy, logical subscriber, read-only projection, or cache. The data and failure guarantees differ. A read replica is not a backup unless retention, isolation, restore, and corruption protection are designed.

## How It Works

In a leader/follower system, the leader records a write in a durable log and streams log records to followers. A synchronous policy waits for a defined follower acknowledgment before reporting commit; asynchronous policy returns before all followers apply it. A follower can be behind due to network, CPU, disk, long snapshots, or a paused process.

Measure lag as bytes/LSN, commit timestamp age, or replay position—not only a boolean “healthy.” Route a read to the leader for read-your-writes, use a session token/commit position to require a follower to catch up, or explicitly allow stale data for a bounded feature. A load balancer health check that only tests TCP does not establish freshness.

Failover requires detecting a failed leader, selecting a sufficiently current follower, fencing the old leader, promoting the new one, updating routes, and reconciling clients in flight. A distributed membership/lease/consensus system may coordinate this; do not imply that a DNS flip alone prevents split brain. Lost acknowledged writes depend on what was synchronously replicated and on the chosen RPO.

## Example

An orders API receives 1,000 writes/s and 20,000 reads/s. A single primary handles correctness-critical order writes; two asynchronous followers serve order history. The naive router sends every read to followers. After a customer places an order, the confirmation page is routed to a lagging follower and says “order not found.”

The improvement routes the write response's session/commit token with subsequent customer reads, or sends a bounded post-write read to the primary until the follower catches up. Stale-tolerant reporting can continue using followers. If followers lag beyond a threshold, the router removes them from fresh-read eligibility rather than pretending they are healthy. The new trade-off is primary load, more routing state, and a possible availability reduction for fresh reads.

For failover, suppose the leader acknowledges a write after local fsync but before follower receipt. A crash can lose that write under asynchronous replication. The system should state whether the order may be retried/reconciled, what the client sees, and whether the API's “success” contract accepts that RPO. A synchronous follower in another availability zone reduces this loss window but adds cross-zone latency and a dependency on that follower.

## Scaling Behavior

Read replicas scale read capacity only for workloads that tolerate their freshness and do not saturate the leader's WAL/network. More replicas multiply log shipping, storage, backups, and failover candidates. Synchronous replicas add a latency term to every write and can reduce write availability.

As data and write rates grow, replication bandwidth, apply throughput, index maintenance, vacuum/compaction, and lag catch-up time become capacity constraints. Sharding may scale write ownership, but each shard now has its own replica set and cross-shard read/failover behavior. Multi-region replication adds distance, conflict, data-residency, and recovery decisions.

## Failure Modes

- **Replication lag:** Followers return stale data or consume storage/log retention while catching up.
- **Acknowledgment ambiguity:** Client times out after a commit; retry must be idempotent and route to an authority.
- **Primary loss:** Promotion chooses a stale follower, losing acknowledged async writes within RPO.
- **Split brain:** Old and new leaders accept writes without fencing, producing divergent histories.
- **Cascading replica overload:** All followers fall behind, then catch up while serving reads and increase disk/CPU pressure.
- **Corrupt/bad write replication:** Replication faithfully copies a deletion or bug; it is not an isolated backup.
- **Failover route cache:** Clients keep sending writes to the old endpoint or pool.

Mitigate with lag-aware routing, synchronous policy aligned with RPO, fencing/leases, idempotency, restore-tested backups/PITR, bounded catch-up, and failover drills.

## Trade-offs

Replication improves read capacity, fault tolerance, and locality but costs storage, log bandwidth, operational complexity, and potentially consistency/latency. Synchronous copies reduce acknowledged-loss risk at a write-latency/availability cost. Async copies preserve a fast write path but expose lag and RPO. More copies do not protect against a bad write or coordinated operator action.

## Alternatives

- **Read cache:** Lower-latency repeated reads; must handle invalidation and does not replace durable failover.
- **Partitioning/sharding:** Adds write and storage ownership instead of only copies; rebalancing is a separate problem.
- **Backup/PITR:** Recovers from corruption/operator error; usually not a low-latency read replica.
- **Multi-region active/active:** Local writes and availability at the cost of conflict/version semantics.
- **Quorum/leaderless replication:** Tunable read/write acknowledgment; requires version resolution and repair discipline.

## When to Use

Use replication when the requirement names read scale, failure-domain survival, local read latency, or a defined recovery objective. State the write authority, acknowledgment, freshness, promotion, fencing, and RPO/RTO behavior.

## When Not to Use

Do not add read replicas to fix an unindexed query or a write bottleneck. Do not route correctness-critical reads to eventually consistent copies without a freshness protocol. Do not call a replica a backup without independent retention and restore tests.

## Common Misconceptions

- **A replica is always current.** Lag is normal and must be measured/routed.
- **Async replication is durable enough by default.** Acknowledged data can be lost within the configured RPO.
- **Failover is a DNS update.** Fencing, promotion, clients, in-flight writes, and split-brain prevention matter.
- **More replicas increase write capacity.** They often add write propagation work; sharding changes ownership.
- **Replication protects from bad data.** It usually copies the bad write quickly; backups/PITR provide another recovery line.

## Interview Lens

### 30-Second Explanation

> I use a primary for writes and replicas for a stated purpose: read scale, locality, or failure recovery. I define whether commit waits for a follower, measure lag, route read-your-writes to a current authority, and specify promotion, fencing, RPO, and RTO. Async replicas can be stale or lose acknowledged writes; synchronous replicas cost latency/availability. Replication is not a backup against corruption or operator error.

### When to Introduce It

Introduce replication after identifying read/write pressure, failure domains, and freshness/durability objectives. Choose read replicas, synchronous copies, sharding, or backups for the actual bottleneck.

### Common Follow-Ups

- What happens to a read immediately after a write?
- How much acknowledged data can failover lose?
- How do you prevent split brain?
- How do you know a replica is safe to promote?
- What happens when a replica is lagging or rebuilding?

### Common Candidate Mistakes

- Treating replicas as independent writers without conflict semantics.
- Claiming zero data loss with asynchronous replication.
- Using a basic health check as a freshness check.
- Forgetting client connection pools/routes after promotion.
- Calling replication a backup or disaster-recovery plan by itself.

## Summary

- Replication copies state; the protocol defines ordering, acknowledgment, freshness, and failover.
- Read replicas trade freshness and routing complexity for read capacity.
- Synchronous replication trades write latency/availability for a smaller loss window; async replication exposes RPO.
- Safe promotion needs fencing, lag awareness, client routing, and tested recovery—not only a DNS change.
