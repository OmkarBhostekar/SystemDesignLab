# Secrets Management

> A secret is authority that must have an owner and expiry path; storing it safely is only one step in a lifecycle that includes delivery, use, rotation, revocation, audit, and recovery.

## Why This Exists

Database passwords, signing keys, API credentials, private certificates, and encryption keys are often copied into source code, images, tickets, environment dumps, or logs. The naive design puts one long-lived credential in a configuration file and grants it to every service. A source leak or one compromised workload then becomes a fleet-wide incident, and nobody knows which copies to rotate.

Secrets management treats credentials as high-impact state. The architecture must answer who may mint/use/read a secret, where it is stored, how a workload bootstraps access, how rotation avoids downtime, how a leak is detected and revoked, and how old data remains recoverable. The goal is to minimize plaintext copies and authority duration, not to create a magical “vault” boundary.

## Mental Model

```text
generate → store → authenticate workload → deliver short-lived secret
    ↑                                     ↓
revoke ← detect leak ← audit use ← rotate/replace → destroy old copy
```

Classify the item: a password/token grants access; a signing key can mint identity; an encryption key protects data; a certificate/private key authenticates a service; ordinary configuration may be public or low sensitivity. Each class has different rotation and recovery requirements. Separate data-encryption keys from key-encryption/authority keys so a service cannot automatically mint or unwrap unrelated data.

The secret store is another trust boundary, not the whole threat model. A workload needs an identity to fetch a secret (“secret zero”), the delivery channel can leak it, the process can dump it, and logs/telemetry can capture it. Restrict both read and use permissions, and prefer a service API or file descriptor with controlled lifetime over copying a durable secret into broad process metadata.

## How It Works

1. Inventory secrets, owner, consumer, purpose, scope, expiry, rotation method, and recovery dependency. Reject unknown/orphaned credentials.
2. Generate high-entropy values or keys in a controlled boundary. Do not invent cryptography or derive production secrets from predictable identifiers.
3. Store encrypted secrets with access policy, version, metadata, audit trail, and retention/destruction rules. Separate production and non-production authority.
4. Authenticate workloads with an identity that is narrower and shorter-lived than the secret it fetches. Bootstrap that identity through a protected platform boundary, certificate, hardware/root process, or manually controlled enrollment—not a shared hardcoded super-secret.
5. Deliver only the required secret to the required workload, keep it out of logs/URLs, and avoid copying it into traces, crash dumps, or client bundles.
6. Rotate proactively with overlapping versions and consumers that can reload safely. Revoke immediately on suspected compromise, then inspect use logs and rotate dependent credentials.
7. Test recovery: a deleted key, unavailable secret store, expired certificate, and restored backup must have an owner and documented behavior.

Rotation is a distributed rollout. A producer may need to accept old and new credentials during overlap; consumers need to refresh without restarting the entire fleet; caches need a max age. Revocation can block new use but cannot erase plaintext already read or copies in backups. Keep a short audit trail of accesses and administrative changes while respecting privacy.

## Example

An invoice service needs database credentials and a signing key. At startup its workload identity requests a versioned DB credential with read/write scope limited to invoice tables and a signing key that can sign invoice links but cannot decrypt backups. The service watches for a new version, tests it, then switches connections. During rotation the database accepts old and new credentials briefly; after all instances report the new version, the old one is revoked.

If a log accidentally contains the old password, the response is not merely deleting the log: revoke/rotate the credential, search audit records for use, invalidate related sessions, and assess exfiltration. If the secret store is unavailable, the service may continue with an already loaded credential for a bounded lease or fail closed for new sensitive operations; it must not fetch from a developer’s fallback file in production.

## Scaling Behavior

A central secret store can become a startup and refresh hotspot; cache only for a bounded lease and avoid every request fetching a secret. Large fleets need push/pull rotation, jitter, rate limits, regional replicas, and backpressure. Per-workload or per-tenant credentials improve isolation but increase inventory, issuance, and revocation volume.

Short-lived credentials reduce compromise windows but increase identity and refresh traffic. Dynamic credentials can simplify rotation but make outages and bootstrap dependencies more visible. Backup/recovery systems need key metadata and access paths that are separated from ordinary application credentials; otherwise a recovery operator or compromised service can decrypt everything.

## Failure Modes

- **Secret in source/image:** repositories and artifact caches retain copies after deletion.
- **Secret zero:** workload bootstrap uses one shared credential that grants broad access.
- **Overbroad read policy:** a service can fetch unrelated signing, database, or tenant keys.
- **Rotation split-brain:** some instances use old credentials and others new ones without overlap.
- **Store outage:** startup/reload fails or services fall back to unsafe local files.
- **Log/crash leakage:** plaintext appears in traces, error dumps, or support tooling.
- **Orphaned secret:** no owner, expiry, or consumer remains but authority is still valid.
- **Key loss:** encrypted data or backups cannot be recovered because key lifecycle was not tested.

## Trade-offs

Central management improves inventory, policy, rotation, and audit but introduces availability and bootstrap dependencies. Short-lived/dynamic credentials reduce exposure but increase refresh complexity and load. Per-service/tenant credentials limit blast radius but multiply operations. Caching protects the application from store outages but delays revocation. Strict fail-closed behavior protects authority but may reduce availability; define safe read-only/degraded modes explicitly.

## Alternatives

- **Environment variables:** convenient for process startup but can leak through dumps, child processes, diagnostics, and orchestration metadata.
- **Mounted files:** make reload and permissions manageable, but file copies/backups and readers remain a risk.
- **Hardware-backed key operations:** reduce key extraction and support signing/decryption boundaries, with cost and availability complexity.
- **Manual credential rotation:** acceptable for a tiny low-risk system, but does not scale or provide reliable evidence.

## When to Use

Use lifecycle-managed secrets whenever a workload needs credentials, private keys, certificates, or encryption authority. Assign owners and expiry before shipping the first secret, and design leak response alongside normal rotation.

## When Not to Use

Do not put non-sensitive configuration into a secret path merely to avoid design work, and do not build a custom cryptographic store. Do not share one credential across unrelated services or tenants because it is easier to deploy.

## Common Misconceptions

- **“A secret manager means the secret is never exposed.”** The consumer still receives authority and may leak it.
- **“Deleting a leaked value from Git fixes the leak.”** Artifact, logs, clones, and attacker copies remain.
- **“Rotation is a cron job.”** It is a coordinated rollout with overlap, reload, revocation, and recovery.
- **“Environment variables are safe because they are not files.”** Process metadata and diagnostics can expose them.
- **“Encryption keys and app passwords have the same lifecycle.”** Their blast radius and recovery constraints differ.

## Interview Lens

### 30-Second Explanation

> I inventory each secret’s owner, consumer, scope, expiry, and recovery path. Workloads authenticate with narrow identities, fetch only what they need, avoid logs/URLs, and reload versioned credentials during overlap. Rotation and revocation are tested distributed rollouts; a leak triggers replacement and blast-radius investigation, while store outage behavior is explicit rather than falling back to a hardcoded credential.

### When to Introduce It

Introduce secrets lifecycle design when the architecture has databases, signing/encryption, third-party APIs, certificates, or tenant-specific credentials. Ask how the first workload authenticates to obtain a secret.

### Common Follow-Ups

- How do you handle secret zero?
- What happens during rotation if half the fleet has the new value?
- How quickly can a compromised key be revoked?
- Can the service read production secrets from a test environment?

### Common Candidate Mistakes

- Saying “put it in environment variables” without leak analysis.
- Using one shared super-secret for all services.
- Rotating without overlap, reload, or recovery testing.
- Deleting logs instead of revoking the leaked credential.

## Summary

Secrets are authority with a lifecycle. Narrow access, authenticate workloads, minimize copies, rotate with overlap, revoke on compromise, audit use, and test recovery. A secret store reduces risk only when bootstrap, consumer, and operational boundaries are designed too.
