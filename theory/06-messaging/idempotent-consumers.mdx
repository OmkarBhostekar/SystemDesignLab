# Idempotent Consumers

> At-least-once delivery is practical only when processing the same logical command twice produces one acceptable business effect.

## Why This Exists

A notification worker sends an email, then crashes before acknowledging. The broker redelivers the message, and the user receives two emails. The naive fix is to reduce retries or acknowledge first, which trades duplicates for lost notifications. An idempotent consumer records which logical operation it has applied and makes repeats no-ops or converge to the same state.

## Mental Model

```text
message(event_id) → dedup check → atomic business effect + record(event_id) → ack
                         │
                         └ duplicate → return prior outcome / no-op
```

An operation is idempotent if repeating it has the same observable result as applying it once. `SET profile.status = active` is naturally idempotent; `balance += 10` is not unless the increment has a unique operation ID. A broker delivery ID may change on redelivery, so use a producer-assigned event ID or business idempotency key with a defined scope.

## How It Works

The strongest pattern stores an inbox/dedup row and the business update in one database transaction:

```sql
INSERT INTO processed_events(event_id, processed_at)
VALUES (:event_id, now());
-- unique(event_id) rejects a repeat
UPDATE orders SET status = 'confirmed' WHERE id = :order_id;
COMMIT;
```

If the insert conflicts, return the recorded result or safely acknowledge. For a state transition, include an expected version (`UPDATE ... WHERE version = 7`) so retries cannot apply an older event after a newer one. For external effects, pass the same idempotency key to the provider when supported and store the request/outcome; otherwise use reconciliation for ambiguous responses.

Do not mark an event processed before the effect commits. If the process crashes after marking but before the effect, a retry can be skipped and the effect lost. If the effect and marker cannot share a transaction, use an outbox, provider idempotency, or a repair job.

## Example

`ChargeRequested(event_id=evt-9, order_id=123, amount=5000)` arrives twice. The billing database inserts `evt-9` into `processed_events` and creates one payment attempt in the same transaction. A retry sees the unique conflict and returns the existing attempt ID. The payment provider receives `idempotency_key=evt-9`; if the network times out, reconciliation asks for the provider's status rather than blindly charging again.

The naive consumer uses `balance += amount` and stores no ID. The improvement adds a unique operation record and versioned update. The new trade-off is storage retention, cleanup, and a failure path for an external provider that does not support idempotency.

## Scaling Behavior

Dedup state grows with event volume and retention. Partition or index by event ID/tenant, and expire only after the maximum duplicate/replay window. High-cardinality idempotency keys need storage capacity and a cleanup strategy. If a single entity is hot, serialize its state transition or use compare-and-set rather than a global lock.

## Failure Modes

- Event ID is generated by the consumer, so each redelivery looks new.
- Dedup row commits before the business effect.
- Event IDs collide across tenants or command types because scope is missing.
- Cleanup expires a key while a delayed redelivery is still possible.
- External provider acts, response is lost, and retry creates an unknown duplicate.
- Non-idempotent side effect occurs outside the database transaction.

Use namespaced stable IDs, atomic inbox/effect transactions, provider keys, version checks, replay windows, and reconciliation dashboards.

## Trade-offs

Idempotency converts duplicate delivery into stored state, index work, and retention policy. Atomic local transactions give strong guarantees within one database but not across external systems. Natural idempotence is cheap but may not fit increment-like operations. A dedup table can grow large and does not protect against semantically different commands that happen to share an ID.

## Alternatives

- **Naturally idempotent upsert:** prefer for projections and status updates.
- **Unique business constraint:** use when the effect has a natural uniqueness key, such as one reservation per request.
- **Transactional outbox/inbox:** couple local state and message/effect atomically.
- **Compensating action:** use when an external side effect cannot be made idempotent and a duplicate must be repaired.

## When to Use

Use idempotent consumers as the default for at-least-once delivery, retries, replay, and any side effect that can be repeated after a crash.

## When Not to Use

Do not assume a short in-memory set is sufficient for a multi-process or long-replay system. Do not use an event ID as a dedup key if two legitimate operations can share it.

## Common Misconceptions

- **Idempotent means never executes twice.** It may execute twice; the observable effect converges.
- **Broker message ID is always stable.** Redelivery IDs and producer retries vary by system.
- **Insert processed row first is safe.** A crash can lose the effect.
- **A dedup table solves external payment duplicates.** It cannot roll back a provider call outside its transaction.

## Interview Lens

### 30-Second Explanation

> Because queues commonly deliver at least once, every consumer gets a stable event or idempotency key. I store it with the business effect in one local transaction, use unique constraints or compare-and-set for state, and acknowledge only after commit. For external APIs I pass the same provider key and reconcile unknown outcomes. The cost is dedup storage, retention, and cleanup, but it protects correctness across crash retries.

### When to Introduce It

Introduce idempotency whenever a message can be retried, replayed, or acknowledged after an external side effect.

### Common Follow-Ups

- Where does the key come from?
- How long is it retained?
- What if the consumer crashes between marker and effect?
- How do you handle a provider timeout?

### Common Candidate Mistakes

They dedup in process memory, use consumer delivery IDs, or write the processed marker before the business transaction.

## Summary

- At-least-once delivery needs duplicate-safe consumers.
- Stable IDs, unique constraints, inbox rows, and atomic effects make retries converge.
- External effects require provider idempotency or reconciliation; local dedup cannot roll them back.
- Retention scope, tenant namespace, and cleanup are part of correctness.
